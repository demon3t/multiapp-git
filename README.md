# mGit

mGit — приложение для Windows 10/11, которое хранит версии конфигурации Apache Superset в обычном Git-репозитории. В снимок входят дашборды, графики, датасеты с колонками и метриками, определения подключений и сохранённые SQL-запросы.

## Установка

1. Установите Git for Windows с Git Credential Manager. Путь к Git должен быть доступен в PATH.
2. Скачайте и запустите [mGit-Windows-x64-Setup.exe](https://github.com/demon3t/multiapp-git/releases/latest/download/mGit-Windows-x64-Setup.exe). Для скачивания нужен доступ к репозиторию GitHub. Сборка x64 без подписи.
3. Для коммитов настройте Git user.name и user.email в локальном репозитории или глобальном профиле.

## Экспорт и импорт

1. Подготовьте локальный Git-репозиторий. Клонировать HTTPS-репозиторий можно в разделе **Репозитории**. Git использует собственный credential helper. При пустом репозитории mGit может записать снимок в текущую начальную ветку.
2. В разделе **Приложения** нажмите **Добавить приложение**, выберите тип **Apache Superset** и папку Git, затем укажите URL и данные для входа. Приложение появится во вкладках. Если вы обновились со старой версии, откройте сохранённое подключение через **Изменить** и укажите папку Git.
3. Нажмите **Проверить** в списке приложений. mGit покажет доступные сведения о версии, роли и API. Для полного пакетного снимка используйте учётную запись с правами чтения и экспорта всех объектов. Роль Admin требуется для штатного HTTP-импорта и последующей сверки цели. Корпоративный CA в формате PEM можно добавить при редактировании в **Дополнительных параметрах Superset**. Пароли, токены и строки подключений шифруются Windows DPAPI.
4. Дважды щёлкните по ветке в боковой панели. Git переключит рабочую ветку и обновит файлы. В списке локальных веток она получит отметку «Текущая». Двойной щелчок по удалённой ветке без локального аналога создаст отслеживающую локальную ветку. Одиночный щелчок открывает историю.
5. Нажмите **EXPORT**. mGit читает страницы пяти списков API, выгружает ZIP по ID, уменьшает пакеты при тайм-ауте или ошибке шлюза и сверяет UUID со списками. Во время выгрузки приостановите редактирование объектов на источнике. Приложение очищает параметры подключений, записывает YAML в рабочую папку. Откройте **Рабочее дерево**, чтобы посмотреть изменения снимка. Для публикации проверьте diff, создайте коммит и отправьте ветку через **Push**.
6. Добавьте профиль целевого Superset с нужным репозиторием. Один раз задайте в дополнительных параметрах строку «UUID пробел SQLAlchemy URI» для каждого подключения. UUID доступен в YAML. При смене URL mGit требует заново задать пароль и подключения.
7. Нажмите **IMPORT**. mGit берёт снимок из текущего коммита рабочей ветки, проверяет совместимость, сохраняет резервный экспорт в папке backups профиля mGit, загружает снимок и сверяет UUID и связи. Для неполного снимка приложение импортирует совместимые объекты и показывает список исключений с причинами. При неопределённом результате mGit оставляет файл блокировки. Перед снятием блокировки проверьте журнал Superset и убедитесь, что сервер завершил предыдущий импорт.

Для обоих действий mGit ищет в текущем коммите snapshots/<ветка>/assets, затем snapshots/superset/assets, затем единственный найденный каталог снимка. При первом экспорте приложение создаёт каталог для ветки. Для сохранённых снимков действует лимит 64 МиБ.

## Установка через адаптер Superset

Запускайте `restore` внутри runtime целевого Superset. Подготовьте отдельную пустую БД метаданных, `SUPERSET_CONFIG_PATH`, секретный `SECRET_KEY` и `APP_NAME`. Выполните `superset db upgrade`, `superset init` и при необходимости `superset fab create-admin`. Для существующей цели предварительно проверьте резервную копию БД метаданных. Установите драйверы и PyYAML, требуемые адаптером поставки.

Передайте `SUPERSET_DATABASE_BINDINGS` из хранилища в окружение процесса. JSON должен содержать все UUID Подключений с объектами `sqlalchemy_uri` и, при необходимости, `extra`. Для проверки используйте локальные тестовые подключения. Передайте SHA256 файла `restore_assets.py` из метаданных поставки. Команда берёт снимок из выбранной ветки Git и вычисляет commit автоматически.

```bash
node dist/cli.js restore --repo "$WORK_DIR" --ref "$EXPORT_BRANCH" \
  --folder "$ASSETS_RELATIVE_PATH" --adapter "$ADAPTER_PATH" \
  --adapter-sha256 "$ADAPTER_SHA256" --target-name "$TARGET_NAME" \
  --owner "$OWNER" --log "$LOG_PATH"
```

Для предварительной проверки ожидается код 0 и этап `validate` в ответе mGit. Если снимок содержит подтверждённые графики без датасета, передайте `--source-orphans "$SOURCE_ORPHANS_PATH"` с `source_commit` именно этого снимка. Подтверждение получают из источника и хранят отдельно от YAML вместе с адаптером. Для установки добавьте `--apply` и укажите новый файл журнала. mGit повторяет предварительную проверку, ожидает `phase=verified` от адаптера и запускает отдельную сверку. Для самостоятельной сверки используйте `--verify-only`. После повторной установки сравните UUID/ID и количества. Проверьте журналы, списки дашбордов и графиков, права и согласованные отчёты на цели.

Используйте адаптер, проверенный для версии целевого Superset и выбранного снимка. При ошибке после начала установки проверьте состояние целевой БД и журнал до снятия блокировки. Журнал mGit содержит этапы и коды завершения.

## Сборка и запуск из исходников

Требуются Node.js 24 и Git. В PowerShell из корня проекта выполните:

    npm ci
    npm start
    npm test
    npm run dist

Установщик появится в release. Распакованная сборка находится в release/win-unpacked. Исходники ядра находятся в src/core, Electron в src/main.ts и src/preload.ts, интерфейс в src/ui.tsx, CLI в src/cli.ts.

## CLI

После npm run build вызовите node dist/cli.js --help. Команды validate, export, plan, import и verify принимают --repo, --folder и полный --commit. Для export этот SHA должен совпасть с HEAD. По умолчанию export возвращает сводку, ключ --write записывает просмотренный снимок. Команда import выполняет новую предварительную проверку и требует --apply. Для целевых операций укажите --target и --environment. Для PROD укажите также --name и --confirm с названием и SHA через пробел. --ca принимает путь к PEM. --backup указывает новый путь для ZIP перед импортом.

Пример локальной проверки:

    node dist/cli.js validate --repo D:\repos\metadata --folder snapshots/test/assets --commit <полный-SHA>

Ключ `--compatible-only` включает режим **Частичный снимок** для команд `validate`, `plan`, `import` и `verify`. Результат JSON содержит список `excluded` с путями и причинами исключения.

Передавайте секреты через переменные среды CI или защищённые переменные процесса. Для доступа используйте MGIT_TOKEN или MGIT_USERNAME и MGIT_PASSWORD. Для импорта задайте MGIT_CONNECTIONS_JSON с отображением UUID на SQLAlchemy URI. CLI возвращает JSON. Коды выхода: 0 — успех, 1 — операционная ошибка, 2 — параметры, 3 — ошибки валидации или проверки результата, 4 — сервер не подтвердил применение.

## Проверки

Модульные тесты проверяют YAML и зависимости, фильтрацию секретов, работу с локальным Git, сетевой таймаут и истечение авторизации. После сборки установщика команда node --test tests/desktop.cjs проверяет запуск упакованного приложения и защищённое сохранение профиля. Интеграционный тест запускается против отдельных локальных Superset 6.1.0 c синтетическими метаданными и выделенным PostgreSQL без опубликованного порта. Для воспроизведения выполните в двух терминалах:

    docker compose -p mgit-integration -f tests/superset/compose.yml up
    npm run test:integration

Вторую команду запускайте после готовности обоих API на портах 18088 и 18089. Тест проверяет пакетный экспорт всех пяти типов, запись и коммит через Git, неизменность YAML объектов при повторном экспорте, резервный экспорт, HTTP-импорт из SHA, проверку связей и отсутствие дублей после повторного импорта. Все учётные данные из тестовых файлов относятся к локальным контейнерам.

## Обновления

Нажмите значок обновления **↻** в верхней строке или **Ctrl+Shift+U**. mGit проверяет публичные релизы GitHub без токена. Если доступна более новая версия, откроется окно со списком изменений.

Нажмите **Обновить**, чтобы скачать установщик, проверить размер и SHA256, установить обновление и перезапустить mGit. Нажмите **Отмена**, чтобы закрыть окно. Доступные параметры автоматической проверки и установки находятся в меню **Приложение → Настройки обновлений**.

GitHub Actions проверяет и собирает Windows x64 на каждом PR в `main`. После push в `main` установщик публикуется в GitHub Releases с тегом `v<версия>-build.<номер запуска>` и постоянным именем файла. Workflow также можно запустить вручную из `main`.

## Ограничения 0.3.1

- Сквозной сценарий рассчитан на Superset 6.1.0 и ZIP assets 1.0.0. Другие версии Superset, корпоративный CA и реальный Azure DevOps/TFS требуют проверки в соответствующих окружениях. HTTPS-адрес Azure DevOps/TFS передаётся Git без преобразования пути.
- Вход поддерживает локальную учётную запись Superset и bearer access token. Интерактивный SSO, автоматическое обновление внешнего токена, SSH-туннели и секретные параметры драйверов пока не поддерживаются.
- Интеграция ограничена пятью заявленными типами. Темы, отдельные файлы данных, дополнительные типы объектов и нераспознанные файлы блокируются. Проверка формата локальная, окончательную проверку схемы даёт API Superset.
- URI в YAML заменяется нейтральным значением mGit. Проверка секретов эвристическая. Просматривайте diff перед коммитом, особенно поля, где можно хранить произвольный текст или SQL.
- Штатный импорт Superset может обращаться к целевым аналитическим подключениям и обновляет объекты по UUID. Тестирование подтверждает UUID, типы и связи, а не полное совпадение всех сериализованных полей. Удаление объектов на цели и автоматический откат отсутствуют. Блокировка защищает запуск из mGit и CLI в пределах временного каталога одного пользователя, параллельные изменения из других клиентов контролирует сервер.
- Git-интерфейс поддерживает работу с выбранной веткой, fetch, push в origin и коммит просмотренного снимка. Разрешение конфликтов, merge и создание PR выполняются внешними средствами.
